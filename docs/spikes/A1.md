# Spike A1: full mode without root

**Verdict: PASS for apps that allow playback capture; full mode is viable.**
- Without root, Sorus can capture other apps' audio, process it and play it back.
- It silences the originals, so the user hears only the processed audio.
- It needs no PC at runtime and survived 11 minutes with the screen off.
- **Some app audio does not reach the capture**, at least some of the time. Spotify's AAudio stream did not reach it at first; about a minute later it did, and Spotify was processed. Sorus must check capturability continuously, and use session mode for whatever doesn't reach the capture.

Two rows of the protocol are still open: YouTube Music and a game, and a second Android 13+ device.

Date: 2026-11-08. Code: `spikes/a1/` (throwaway; Kotlin, plain Views, Shizuku API 13.1.5).

## How it works (learned from RootlessJamesDSP, GPL-3.0)

1. **Permissions, once, through Shizuku.** Shizuku runs as the shell user. The app uses it to run:
   - `appops set <pkg> PROJECT_MEDIA allow`
   - `pm grant <pkg> RECORD_AUDIO`
   - `pm grant <pkg> POST_NOTIFICATIONS`

   With `PROJECT_MEDIA` allowed, `createScreenCaptureIntent()` returns immediately with no consent dialog.
2. **Capture.** `AudioPlaybackCaptureConfiguration` matches `USAGE_MEDIA`, `USAGE_GAME` and `USAGE_UNKNOWN`, and excludes Sorus's own uid. The app records 48 kHz float stereo through a foreground service of type `mediaProjection`, holding a partial wake lock.
3. **Process.** A fixed +6 dB low shelf at 100 Hz (Kotlin biquad; a checkbox bypasses it so the effect is audible). Playback goes through an `AudioTrack` (`USAGE_MEDIA`, `ALLOW_CAPTURE_BY_NONE`, low-latency mode, 10 ms blocks).
4. **Silence the originals.** Android's playback capture duplicates audio: the AOSP route flags are `LOOP_BACK | RENDER`, so the original keeps playing. RootlessJamesDSP's trick, reproduced here:
   - attach a `DynamicsProcessing` effect with −200 dB input gain and priority `Int.MAX_VALUE` to each playing session;
   - session effects only run on the speaker path, so the captured copy is untouched.
5. **Find sessions** by parsing `dumpsys audio` through Shizuku once per second. The relevant fields are `u/pid:`, `usage=`, `flags=0x…` and `sessionId:`. Format checked on Android 16 One UI and on the Android 17 emulator.

- Shizuku was started on the phone via wireless debugging.
- The APK was installed over USB.
- No PC was involved at runtime.

## Findings that change the product plan

1. **Hybrid per-app mode (new design point).** Full mode cannot process apps whose audio doesn't reach playback capture: AAudio apps such as Spotify, and apps that set `FLAG_NO_MEDIA_PROJECTION`. Sorus must:
   - check that a session's audio actually reaches the capture before keeping it muted (the spike watches for 1.5 s of silent capture while the session plays);
   - fall back to **session mode** (DynamicsProcessing EQ on that app's own session) for those apps.

   **Don't decide this from the mixed capture.** The first heuristic was "mixed capture silent for 1.5 s while the session plays". It misfired on a gap between songs: it unmuted com.mero, and the next song played twice (an echo). The fix is a capture of that uid alone (`addMatchingUid`, 250 ms):
   - unmute only when that capture hears nothing;
   - re-probe unmuted sessions every second and mute them again when their audio appears.

   The product should keep a per-app capture tap so this check is continuous rather than probed. The check must
   work **per session, not per uid**. Spotify ran a capturable and an uncapturable session side by side, and a
   uid-wide probe can't tell them apart: a uid-wide decision mutes both, which silences the uncapturable one.

   Spotify does announce its session, so session mode should reach it. A2 will confirm. The UI must show per app which mode is active.
2. **Mute debounce.** `dumpsys` sometimes misses a live player for one poll. Releasing the mute right away caused flicker, so the original leaked through. Keep a mute until the session has been missing for 3 consecutive polls.
3. **Session-effect conflicts.** Muting uses `DynamicsProcessing` on other apps' sessions. Other EQ apps doing the same will fight over the session. After a process restart, the old effect can block a new one for one poll (`Error -3`); a retry on the next poll works.
4. **Shizuku lifetime is a UX cost.** Wireless debugging (and with it Shizuku) stops after reboots and some Wi-Fi changes. Onboarding must make restarting Shizuku easy and detect when it has stopped.
5. **Latency and underruns belong in A4.** The Kotlin `AudioTrack` loop with 10 ms blocks is fine for a go/no-go test. A4 should move it to the C++ core + Oboe and measure added latency.
6. **Edge-to-edge.** On Android 15+ the window draws under the system bars, so UI must handle insets (it bit the spike).
