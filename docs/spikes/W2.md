# Spike W2: UI ↔ APO settings path

**Verdict: PASS** for live changes and after an audio-service restart. The sign-out/sign-in check was skipped by the owner.
A normal (non-admin) program changed the gain of the APO running inside `audiodg.exe` through shared memory. Each change
applied within **1.1–9.4 ms** of the write, and the level moved by exactly the set amount.

Date: 2026-11-08. Machine: owner's PC, Windows 11 25H2, Realtek onboard speakers. Code: `spikes/w2/` (throwaway).

## Design (one deliberate change from the protocol)

The protocol had the **app** create the shared-memory section. But a standard user cannot create `Global\` objects
(that needs `SeCreateGlobalPrivilege`), and audiodg (session 0) cannot see a user's `Local\` objects. So the
**APO creates** `Global\SorusW2Control`; LocalService does hold that privilege.
- **DACL** (SDDL): `D:(A;;GA;;;SY)(A;;GA;;;LS)(A;;GA;;;BA)(A;;GRGW;;;IU)`. SYSTEM, LocalService and Administrators get
  full access; interactive users get read and write.
- **Block** (`control.h`): `seq`, `gain_db`, `written_qpc`, `applied_seq`, `applied_qpc`, `apo_instances`.
  - The app writes the gain, then `InterlockedIncrement(seq)`.
  - In `APOProcess` the APO checks `seq` (one acquire load per buffer). On a change it recomputes the gain and stamps `applied_seq` and `applied_qpc`.
  - No locks or allocation on the real-time thread.
- The APO creates the block lazily in `LockForProcess`, once per audiodg process (`std::call_once`).

`w2test.exe` (run as a normal user) does the following:
- opens the block and plays a 1 kHz tone on the endpoint;
- records the endpoint with WASAPI loopback;
- steps the gain 0 → 0 → −6 → −12 → 0 dB, 1.5 s each (the first 0 dB step is an unjudged warm-up);
- reports apply latency from the QPC stamps and the level change against the second step.

## Results

| Condition | Gain steps (set → measured change) | Apply latency | Result |
|---|---|---|---|
| Live, run 1 | 0 → 0.00, −6 → −6.00, −12 → −12.00, 0 → 0.00 | 5.8 / 2.3 / 8.5 / 1.1 ms | PASS |
| Live, run 2 | 0.00 / −6.00 / −12.00 / −0.00 | 9.3 / 4.3 / 4.7 / 9.1 ms | PASS |
| After `Restart-Service audiosrv` | **block missing until audio played**, then 0.00 / −6.00 / −12.00 / −0.00 | 9.1 / 3.7 / 9.4 / 7.5 ms | PASS (see finding 2) |
| After sign-out / sign-in | – | – | skipped by owner |

The first test version reported false failures: it judged the first step, during stream start-up and while the vendor
effects were still settling. Adding the warm-up step fixed this; the APO did not change.

## Findings that change the product plan

1. **Apply latency is bounded by the engine period.** The APO reads settings once per `APOProcess` call, every 10 ms in shared mode. The worst case is therefore one period (≈10 ms), which is at the 10 ms target. That is fine for UI changes. For guaranteed sub-period response, the APO would need a smaller period, and that isn't needed.
2. **The block exists only while an APO instance exists.**
   - After an `audiosrv` restart, the new audiodg creates the block only when the first stream reaches the APO. Until then the app can't connect.
   - Anything written to the old block is gone.

   So in the product:
   - **The APO loads persisted settings itself** at creation, from a file in `ProgramData` (readable by LocalService). Your EQ then applies from the first buffer, with or without the UI running.
   - The UI app **reconnects with retry** and **re-sends its full state** after a reconnect. It can detect a restart from a generation counter in the block.
3. **Every APO instance shares one block.** `apo_instances` grew with each new stream, so one block serves every stream and mode. The product block must therefore carry per-endpoint settings, keyed by endpoint ID.
4. **Security.** Interactive users can write the block, so any logged-in user can change the system EQ. That is acceptable for a sound app. The DACL must not grant write to `Everyone` or to AppContainers.
