# Spike A4: full-mode latency

**Verdict: FAIL against the 40 ms target, and the shortfall cannot be fixed from the app.**
- Full mode delivers audio about **110–120 ms after it is captured**, of which about **82–85 ms is Android's capture path**. Sorus's own processing and output account for 26–31 ms.
- Against the original app's own output path (~56 ms), full mode adds about **55–65 ms**.
- That is inaudible for music, but near the lip-sync threshold for video (audio late by more than ~45 ms is detectable).

Date: 2026-11-08. Device: Galaxy A55 (SM-A556E), Android 16, One UI 8.5, speaker. Source: com.mero playing music.
Code: `spikes/a1/` (`CaptureService.kt`, Kotlin `AudioRecord`/`AudioTrack`; the protocol said Oboe, but its timestamps
measure the same thing).

## Method

The full-mode loop timestamps the same sample at both ends:
- **captured:** `AudioRecord.getTimestamp(MONOTONIC)`, extrapolated to the first frame of each block read;
- **presented:** `AudioTrack.getTimestamp()`, extrapolated to the first frame of the same block once written;
- **received:** `System.nanoTime()` when `read()` returned, which splits the delay into the capture side and the output side.

Each report averages every 10th block over 30 s. The original app's own output path is taken from the audio engine's own data (`dumpsys media.audio_flinger`): com.mero plays on the deep-buffer output, whose write latency averages 56 ms.

The filmed A/V test from the protocol was not run (it needs a second camera).

## Results

| Configuration | Capture → presented | Capture side | Output side | Underruns / 60 s |
|---|---|---|---|---|
| 10 ms blocks, default buffers (record 3072, track 3840 frames) | 117.6–117.8 ms | – | – | 4 |
| 10 ms blocks, track capped to 3 blocks (1440 frames) | 114.7 ms | 84.7 ms | 30.0 ms | 3–6 |
| 10 ms blocks, drop a block when the capture side > 30 ms | 107.7 ms | 81.7 ms | 26.0 ms | **923** (unusable) |
| **5 ms blocks, track capped to 3 blocks (720 frames)** | 115.5–116.0 ms | 84.6–84.9 ms | 30.9–31.1 ms | **1** |

- **Capping the output buffer helped little:** the output side only moves from about 30 to about 26 ms, because Android's fast output path itself accounts for most of it.
- **The capture side is not a backlog.** Dropping blocks didn't bring it below about 82 ms and wrecked playback. The delay is built into the remote-submix capture pipe.
- **5 ms blocks cost no extra latency and were the most stable** (1 underrun per minute). Ship 5 ms blocks.

**Added latency vs. the original:** about 116 ms (capture → speaker) − about 56 ms (original mix → speaker) ≈ **60 ms**,
±10 ms, since the capture timestamp's reference point inside the submix pipe isn't documented.

## What this means for the product

1. **Per-app mode choice includes latency.** Full mode suits music (latency inaudible) and anything without video. For
   **video apps** (YouTube, Instagram, Netflix, Hotstar), Movie mode should default to **session mode** (no added
   latency, a slightly less precise EQ, see A3), with full mode as an opt-in. The per-app routing table from A1/A2 gains a "latency-sensitive" column.
2. **Use 5 ms blocks and cap the output buffer at about 3 blocks.** The capture side can't be shortened from an app, so don't
   try (no drop/skip logic).
3. **The 40 ms target is unreachable without root.** It stays the target for root-based modes and future Android APIs;
   rootless full mode documents its +60 ms honestly in the UI.
4. Moving the loop to C++/Oboe (M5) is still worth doing for CPU and stability, but it won't fix latency: about 85 ms is inside Android.
